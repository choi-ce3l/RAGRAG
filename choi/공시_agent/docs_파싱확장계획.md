# 분기·반기 파싱 확장 계획

작성 2026-08-29 · 대상 `code_chunkingandparsing/src/facts.py`

## 왜

`qa_gold_final.json` 146문항 중 **28건**이 분기·반기 수치를 묻는데 답하지 못한다.
문서는 corpus에 있다 — `chunks.jsonl`에 분기보고서 97,462 · 반기보고서 45,716 청크.
**수치로만 안 뽑혀 있다.**

| 문서 | manifest 건수 | fact 추출 |
|---|---|---|
| 사업보고서 | 291 | ✅ |
| 반기보고서 | 234 | ❌ |
| 분기보고서 | 529 | ❌ |

## 진단 — 파서는 이미 돌아간다

분기보고서로 `extract_facts()`를 직접 호출해보면 **425건이 추출된다.** 파서를 못 쓰는 게
아니라 `build()`가 막고 있다.

```python
# facts.py:270
if e["doc_group"] == "periodic"
and "사업보고서" in (e.get("report_nm") or "")     # ← 여기서 걸린다
```

그런데 필터만 풀면 **틀린 값이 들어간다.** 실제로 삼성전자 분기보고서를 뽑아보면:

```
수익(매출액)  term=55   63,745,371   period_start=None  period_end=None
수익(매출액)  term=54   63,745,371   ← 다른 기수인데 같은 값
수익(매출액)  term=55   42,168,679   ← 같은 계정이 또 나옴
```

## 근본 원인 — 정규식 하나

메타표의 기간 정보를 읽는 정규식이 분기 표기를 못 읽는다.

```python
# facts.py:37
_TERM_RE = re.compile(
    r'제\s*(\d+)\s*기말?\s*(\d{4})\.(\d{2})\.(\d{2})'
    r'(?:\s*부터\s*(\d{4})\.(\d{2})\.(\d{2})\s*까지)?')
```

`제 56 기` 뒤에 바로 날짜가 오는 것을 전제한다. 그런데 실제 원문은:

| 문서 | 메타표 표기 | 현행 매칭 |
|---|---|---|
| 사업보고서 | `제 56 기 2023.01.01 부터 2023.12.31 까지` | ✅ |
| 분기보고서 | `제 56 기 **1분기** 2023.01.01 부터 2023.03.31 까지` | ❌ |
| 반기보고서 | `제 56 기 **반기** 2023.01.01 부터 2023.06.30 까지` | ❌ |
| 분기 시점 | `제 56 기 **1분기**말 2023.03.31 현재` | ❌ |

기수와 날짜 사이의 `1분기`·`반기`가 매칭을 깨뜨린다. 그래서 `terms` 사전이 비고,
`period_start`/`period_end`가 `None`이 되며, 열 배정이 어긋난다.

**표의 구조 자체는 사업보고서와 같다.** 표기만 다르다.

## 단계별 계획

### 1단계 — 기간 표기 인식 (반나절)

정규식이 기간 구분을 흡수하고 **별도 필드로 보존**하게 한다.

```python
_TERM_RE = re.compile(
    r'제\s*(\d+)\s*기\s*((?:[1-4]\s*분기|반기|중간)?)\s*(?:말)?\s*'
    r'(\d{4})\.(\d{2})\.(\d{2})(?:\s*부터\s*(\d{4})\.(\d{2})\.(\d{2})\s*까지)?')
```

네 가지 표기를 모두 매칭하는 것은 확인했다. `terms`의 키를 기수 하나에서
`(기수, 기간구분)`으로 바꾸고, fact 레코드에 `period_type`을 추가한다.

- [ ] `_TERM_RE` 교체 + `terms` 키 확장
- [ ] fact 스키마에 `period_type` 추가 (`annual` / `Q1`~`Q4` / `H1`)
- [ ] 사업보고서 재추출 결과가 **기존과 완전히 동일한지** 대조 (회귀 방지)

### 2단계 — 3개월 vs 누적 구분 (1~2일) ← 진짜 난점

손익계산서·현금흐름표는 **기간** 항목이라 분기보고서에 두 종류 열이 있다.

```
제56기 3분기 3개월    (7~9월 단독)
제56기 3분기 누적     (1~9월 누계)
```

재무상태표는 **시점**이라 이 문제가 없다. 그래서:

- [ ] 데이터표 헤더에서 `3개월` / `누적` 구분자 추출
- [ ] 헤더에 명시가 없으면 **메타표의 `부터~까지` 길이로 판정**
      (1~3월 = 3개월 단독, 1~9월 = 누적)
- [ ] fact에 `cumulative: bool` 추가
- [ ] BS/EF는 이 필드를 비워 둔다

**판정이 불가능하면 그 fact를 버린다.** 3개월인지 누적인지 모르는 수치는
잘못 답하는 것보다 없는 편이 낫다.

### 3단계 — 조회 계층 반영 (반나절)

- [ ] `numqa.FactStore` 인덱스 키에 `period_type` 추가
- [ ] `qa/labelstore.py` 인덱스도 동일하게
- [ ] `qa/period.py`의 분기 인식이 이제 **거절이 아니라 조회**로 이어지게
- [ ] 기간 미지정 질문은 **연간을 기본**으로 (지금 동작 유지)

### 4단계 — 검증 (반나절)

새 데이터가 늘면 틀릴 여지도 는다. 자동 검사를 먼저 붙인다.

- [ ] **누적 정합성**: `Q1 + Q2 + Q3 + Q4 ≈ 연간` (오차 0.5% 이내)
- [ ] **누계 정합성**: `3분기 누적 = Q1 + Q2 + Q3`
- [ ] **기존 회귀**: 사업보고서 fact 213,909건이 그대로인지 대조
- [ ] `qa/hierarchy.py`의 합계 검증을 분기 데이터에도 적용

### 5단계 — 재빌드 및 측정 (반나절)

- [ ] `facts.py build` 필터 확장 → 재빌드
- [ ] 캐시 재생성 (`labelstore` · `hierarchy` · `applicability`)
- [ ] `qa_gold_final.json` 재평가 — 28문항이 열리는지
- [ ] 회귀 확인: `qa_gold.jsonl` 지표가 떨어지지 않는지

**메모리가 관건이다.** 4GB 서버에 워커 1개면 되지만 2개는 어렵다.
필요하면 분기 fact를 별도 저장소로 분리해 지연 로딩한다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 3개월/누적 오판 → **틀린 숫자를 자신 있게 답함** | 판정 불가 시 fact를 버린다. 4단계 검증을 먼저 붙인다 |
| 기존 사업보고서 파싱 회귀 | 1단계에서 재추출 결과를 기존과 완전 대조 |
| 메모리 초과 | 분기 저장소 분리 + 지연 로딩 |
| 기업별 표기 예외 | `parser_confidence`를 낮게 주고 표본 검수 |

## 하지 않을 것

- **LLM으로 표를 읽지 않는다.** 이 프로젝트의 출발점이 "LLM이 표 숫자를 전사하며 오답"이었다.
  구조가 있는 XML을 정규식으로 읽는 편이 정확하고 재현 가능하다.
- **주석(footnote) 표까지 확장하지 않는다.** 핵심 재무제표(BS/IS/CF/EF)로 범위를 유지한다.

## 순서 제안

1단계 → 4단계 검증 → 2단계 → 재검증 → 3·5단계.

**2단계(3개월/누적)를 하기 전에 4단계 검증을 먼저 붙인다.** 틀린 열을 넣고
나중에 발견하는 것보다, 검사를 켜 놓고 넣는 편이 안전하다.

## 검증

- **1단계 회귀** — 사업보고서 12건 재추출, 기존 파서와 차이 0.
  전체 대조에서 213,909 → 213,694(−215)인데, 빠진 215건은 라벨·계정코드·기수가
  모두 없는 `'1265.8%'` 같은 비율 문자열이다. 손실이 아니라 정리다.
- **4단계 누적 단조성** — 497조합 전부 통과 (위반 0).
  `build_facts.py --validate`로 상시 실행 가능.

## 4단계 검증이 실제로 잡아낸 것

처음 빌드에서 **168/497 (34%) 위반**이 났다. 원인은 분기·반기 손익계산서의 2단 헤더였다.

```
행0: ['', '제 50 기 반기', '제 49 기 반기']     ← 병합돼 3칸
행1: ['3개월', '누적', '3개월', '누적']          ← 라벨 열이 없어 4칸
행2: ['매출', v1, v2, v3, v4]                  ← 5칸
```

행0만 헤더로 읽으면 행1이 데이터 행이 되고 열이 한 칸씩 밀린다. **2분기 단독 매출이
반기 누적으로 라벨링됐다.** 값 자체는 맞으니 눈으로는 걸러지지 않는다. 검증을 먼저
켜두지 않았으면 그대로 배포됐을 결함이다.

병합이 풀려 있지 않으므로 칸 수로 배분한다 — 기수 n개가 아랫줄 m칸을 균등하게 나눈다.
고친 뒤 위반 168 → 14 → (단위 스케일 반영 후) **0**.

남은 14건은 기간 문제가 아니라 단위였다. `value_decimal`은 표에 찍힌 그대로라
`scale`을 곱해야 원이 된다. 사업보고서는 백만원, 분기보고서는 원으로 적는 경우가
많아 곱하지 않으면 연간이 9개월보다 작아 보인다.

## 그 밖에 검증이 드러낸 두 결함

1. **정정 이력 62,124건 유실.** `build()`가 `supersede.build_supersede_map()`을 쓰지 않고
   문서를 자기 자신에 매핑해 `is_superseded`가 전부 0이었다. 근거 선택 정책
   (정정 안 된 것 우선 → 최신 접수번호)의 한 축이 죽어 있었다. 좌표 정확도는
   접수번호 정렬이 대신 받쳐줘 46% 근처를 유지했기 때문에 지표만 봐서는 보이지 않았다.

2. **좌표 규칙 오해.** 기존 `fact_id`의 `c55`는 열 번호가 아니라 **기수(제55기)** 였다.
   열 인덱스로 바꿨더니 근거 좌표 정확도가 46.0% → 6.0%로 무너졌다. 정답셋은 원본
   규칙 기준이므로 원본을 따른다.
   다만 그 규칙은 한 표에 같은 기수가 두 열이면 겹친다(분기 3개월/누적). JSONL에는
   PK가 없어 원본에서는 드러나지 않던 문제로, PK를 걸자 30,511건이 조용히 덮어써졌다.
   **표시 좌표(`fact_id`)와 저장 키(`row_key`)를 분리**해 해결했다.

## 3단계 — 런타임 연결

- `.facts`는 **사업보고서만** 유지한다. 분기까지 넣으면 이 목록을 코퍼스 전역 분석에
  쓰는 쪽(concepts·applicability·hierarchy·derived·kg)의 모집단이 바뀐다. 그 분석들은
  연간 기준으로 유도·검증한 것이다.
- 분기·반기는 `lookup(..., period=spec)`으로 SQLite를 직접 친다. period 없이 부르는
  기존 경로는 예전과 같은 인메모리 인덱스를 탄다 — 분기를 묻지 않은 질문의 답이
  바뀌는 일은 없다.
- **1·2·3분기는 `period_label`이 전부 `'3개월'`이라 종료월이 유일한 판별자다.**
- 4분기·하반기는 공시되지 않아 뺄셈으로 만든다 (연간 − 3분기누적 / 연간 − 반기누적).
  단위가 다르거나 결과가 음수면 답하지 않는다.

### 조용히 틀릴 뻔한 지점

붙이는 도중 두 번, **연간 값에 "3분기 기준입니다"라는 안내만 붙는** 상태가 나왔다.

- `stage02_retrieve`가 연간 전용 `store.lookup`을 직접 불렀다.
- `stage03_compute`가 `numqa.answer()`로 **질문을 다시 파싱**해, 찾아둔 분기 fact를
  버리고 연간 답을 만들었다.

둘 다 답을 못 내는 것보다 나쁘다. 기간 질문은 `numqa.answer`로 보내지 않고 우리 fact로
직접 문장화하며, 답변 문장과 순위·합계 문장에 **어느 기간인지 반드시 박는다**.
